# v3: hybrid approval · bilingual quotes · review-due · MVP AI through API keys

- **Topic:** Karthi's answers on the implementation-plan v1 questions (6 Oct 2026).

## 1. Hybrid approval (Q1)

**Chosen:** Claude's proposed design, accepted.

| Situation | Who approves | Label |
|---|---|---|
| Normal case | The surgeon who said it | ✅ Surgeon-approved |
| Surgeon busy | The surgeon gives **written, per-case delegation** to a named clinical owner, who approves; the surgeon can confirm or withdraw later | 👁 Approved by Dr. X on behalf of Surgeon A (delegated) |
| Archive case whose surgeon has left or retired | A clinical owner reviews | 👁 Reviewer-checked (never ✅) |
| Procedure-level summary card (many surgeons) | Clinical owner | 🏥 Department-approved |

- Words are never edited without a new version.
- Patterns show the trust mix, e.g. "3 ✅ + 1 👁".
- Implementation: a `approval_delegation` record (surgeon, delegate, case, scope, granted_at, revoked_at). `card_version` stores `approval_path ∈ {surgeon, delegated, reviewer, department}` and the label is derived from it.
- This **replaces** v1 §4.1 invariant 4 ("approver = case surgeon only").
- Options considered: surgeon only; owner may always approve.

## 2. Japanese quotes in English mode (Q2)

**Chosen: show both.**
- The original Japanese quote is always shown; it is the evidence.
- In English mode an English translation appears under it, marked 🤖 *machine translation*. It is a reading aid, never evidence.
- Japanese mode shows Japanese only, with an optional EN toggle.

## 3. After the review-due date (Q3)

**Chosen:** the card stays visible with ⚠ "review overdue" and is **excluded from patterns and summaries** until it is re-reviewed.

## 4. AI models for the MVP (Q4 discussion)

**Chosen:** for now, all LLM tasks use **closed models through API keys** (gateway profile `dev-cloud`), for development **and** the demo.

| Component | Choice |
|---|---|
| Drafter and verifier | Two **different families**: Claude through AWS Bedrock (`jp.` route, Tokyo) and OpenAI. Which one drafts and which verifies is decided by the P1 benchmark |
| Speech-to-text | Stays local on the laptop (ReazonSpeech-k2 + kotoba-whisper). It is CPU-friendly, and the pilot needs it |
| Embeddings / reranker | Local ruri-v3 (ONNX); a cloud embedding model is a gateway option if needed |

**Consequences:**
- **One laptop** (Surface) runs the app, DB and speech. **No LAN link** and no `ai-host` service are needed for the MVP. The ASUS is a spare demo machine.
- The `local` profile stays in the gateway design (one setting to switch later), but it is **off the MVP critical path**.
- **The demo needs internet.** Mitigations: phone tethering as a backup link; the "prepared lane" (pre-drafted cards, labelled ⏱) if the API is unreachable; a failure-injection rehearsal with the internet cut.
- Data stays synthetic only. The gateway still refuses 🏥 real data to non-Japan providers.
- **Anti-circularity:** practice scripts must be generated by a model family that is neither the drafter nor the verifier. With Claude and OpenAI used for drafting/verifying, scripts come from a third family (a local open model on the ASUS or another API) plus human improvisation (≥ 50%).
