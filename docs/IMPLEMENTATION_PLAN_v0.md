## 1. What "done" means for the MVP

**The MVP is done when both are true:**
1. **L1 pass marks** are met on the synthetic golden set:
   - evidence IDs valid 100%;
   - quotes match 100%;
   - numbers not in the source: 0;
   - planted-PII leaks: 0;
   - negation errors after verification: 0;
   - debrief CER ≤ 10%.
2. **The 6-minute flagship demo** runs end to end on the two laptops: narrate → draft → verify → approve → manual → search.

**In scope (from ch. 3 S0):**
- case intake;
- video import + step template;
- ★ marking;
- clip-anchored voice Q&A;
- single-speaker speech-to-text;
- privacy filter;
- AI drafting with per-field evidence;
- verification;
- term mapping with laterality rules;
- one review queue;
- living manual;
- case detail;
- governance states;
- audit;
- graph-first hybrid search;
- JA + EN;
- honest 🧪 labels.

**Out of scope for the MVP:**
- Prepare brief (S2);
- ASK (V1);
- prospective OR capture (V1);
- video AI;
- hospital SSO;
- cloud hosting;
- real patient data.

## 4. Core contracts (designed first, so phases can be built and tested independently)

### 4.1 Data model (Postgres; from ch. 5 + RS4 §4.6 + the CEO's governance)

| Group | Tables |
|---|---|
| People | `institution` (one in the MVP) · `app_user` · `membership(role)` · roles: surgeon, clinical_owner, junior, admin, tester |
| Case | `procedure` (K-code, JA/EN) · `case` (procedure, side, approach, platform, technique_version, surgeon_pid, **data_class**, status) · `media_asset` (original/proxy/audio/clip, path, sha256, duration, fps, codec, clock_offset_ms) |
| Narration | `step_template` (per surgeon × procedure, versioned) · `narration_session` · `marker` (video_ms, step_id, reason) · `question` (template_id, slots) · `answer` (audio asset, duration) |
| Speech | `utterance` (append-only: source, answer_id, t_start/t_end, video_anchor_ms, speaker_role, text_redacted, engine A/B text, disagreement spans, redaction_stamp, transcript_version) |
| Runs | `pipeline_run` · `stage_run` · `ai_call` (provider, model_id, prompt_version, dictionary_version, input_hash, tokens, cost, latency, data_class) |
| Cards | `card` · `card_version` (state, scope, body JSONB, dictionary_version, run_id, approved_by/at, content_hash, supersedes, privacy_state, release_purposes, review_due, safety_signal) · `card_field` (status, value, value_terms, evidence_kind, verifier_verdict, conf_band) · `evidence_anchor` (utterance range, quote exact/prefix/suffix, char offsets, media t_start/t_end) |
| Dictionary | `term` (kind, status, ltree path, danger_zone, safe_name, replaced_by) · `term_label` (JA/EN pref/alt/hidden/slang) · `term_rel` (part_of, confusable_with, sounds_like) · `term_xref` · `laterality_rule` · `dictionary_release` (semver) |
| Knowledge | `edge` (derived from approved versions) · `card_search` (tokens tsvector, embedding vector, embed_model_id) |
| Audit | `audit_event` (append-only, hash-chained; actor, action, object IDs, at; IDs only, never content) |
| Settings | `institution_setting` (raw-audio retention: explicit choice required) |

**Invariants enforced in the database (not only in code):**
- approved `card_version` rows are immutable (trigger);
- `audit_event` is insert-only;
- every `card_field` with status *filled* has ≥ 1 evidence anchor;
- `why`/`decision`/`alternatives`/`applicability`/`limitations`/`lesson` fields require `evidence_kind` = stated_*;
- the data_class of child rows equals the case's data_class.

### 4.2 Gateway task contracts (JSON-schema validated; same for every provider)

| Task | Input | Output |
|---|---|---|
| `transcribe` | audio, language, vocab hints | segments [{t_start, t_end, text, word timings, conf}] per engine |
| `classify_answer` | question, answer text | {elements: cue/expectancy/option/basis/threshold, dont_know} |
| `draft_card` | case context, marker, utterances (IDs + redacted text), step template, dictionary hints | {type, step_id, fields: {name: {status, value, terms[], evidence: [{utt_id, quote}], evidence_kind}}} |
| `verify_field` | field, value, cited quotes, context | {verdict: supported/partial/unsupported/contradicts, polarity_ok, speaker_ok, stated_vs_inferred} |
| `map_term` | surface text, candidate terms | {term_id \| null, confidence, needs_review} |
| `embed` | texts | vectors + model_id |
| `rerank` | query, docs | scores |

**Every call carries:** `data_class`, a `privacy_stamp` (for real data), a `task_version` and a `profile`.
**Every call returns:** the result + a provenance record (written to `ai_call`).

### 4.3 API surface (MVP)

- **Auth & settings:** `/auth` (local login + role switcher for the demo; OIDC-ready interface) · `/admin/settings` · `/audit`
- **Cases & media:** `/procedures` · `/cases` · `/cases/{id}/media` (chunked upload)
- **Narration:** `/sessions` · `/sessions/{id}/markers` · `/sessions/{id}/next-question` · `/answers` (audio upload)
- **Cards:** `/cards?state=in_review` · `/cards/{id}` · approve / fix / dont-keep / withdraw · `/governance` (privacy clear, release)
- **Knowledge:** `/manual/{procedure}?variant=…` · `/search` · `/dictionary`
- **Operations:** `/health` · `/gateway/benchmarks` (internal)

### 4.4 Job model

- Each block is a **pure stage function** `(inputs) → outputs + provenance`, run by a job runner with an **idempotency key** (the hash of its inputs and versions). The same functions can later run on a hospital box or in Tokyo (portable pipeline, N9).
- **As-you-go drafting:** each answer triggers ASR → privacy → draft → verify → terms, all for that ★ only.
- **Batch re-run** is available per session.

## 7. Synthetic data (fixtures)

- **Procedure:** left laparoscopic adrenalectomy (first pack). All content is labelled 🧪 and marked "to be ratified by a urologist".
- **Script generation:** case outlines → LLM-drafted narration answers (a dev tool; synthetic only) → hand-edited by us → **read aloud by people** (quiet room, a phone-class mic) + TTS copies for regression.
- **Traps planted in scripts:**
  - negation ("don't clip yet");
  - counterfactual ("should have…");
  - no "why" given;
  - numbers;
  - confusable anatomy (adrenal vs inferior phrenic vein);
  - ASR homophones (静脈/動脈);
  - laterality errors;
  - PII (names, dates, IDs);
  - an overgeneralisation.
- **Videos:** synthetic/dry-lab or licence-clean footage only (no Cholec80, no SAR-RARP50). If none is available, a placeholder video with the correct timeline structure is used.
- **Sealing:** answer keys live in `eval/golden/` and are never shown to prompts or tuning runs.

## 8. Engineering rules (from the guardrails)

- Blocks never call a model directly; everything goes through the gateway (task + contract).
- `data_class` is set at case creation and propagates; the gateway refuses 🏥 real data to non-Japan providers in **every** profile.
- The AI fills structure only. Clinical-claim fields must be surgeon-stated or *unknown* (DB constraint + validator).
- Approved = frozen (DB trigger). A change creates a new version needing approval.
- Every AI call is logged with provider, model, prompt version, tokens, cost, latency.
- Secrets live only in `.env` (git-ignored). No keys in code, logs or chat.
- Git: the private repo; only karthi-ai-engineer; no assistant attribution; commit and push only when Karthi asks.
- Cross-platform rule: every library must work on Windows-ARM64 and Linux-ARM64 (CI enforces it).
